# Assignment 1 Reflection

## What was the breakthrough that moved the work forward?

The main breakthrough was not a technical fix. It was recognising that a working implementation could still be the wrong answer.

The first version already had the core mathematics and interaction in place. Clicking the button changed the fold count, the thickness doubled correctly, and the comparison object changed with the scale. On paper, most of the important pieces were there. But when I used it, it still felt like a dashboard displaying results rather than an explainer about folding paper.

That changed how I approached the rest of the project. Instead of asking Claude to keep improving the existing layout, I stopped implementation and reconsidered the interaction itself. The paper needed to remain part of one continuous world, and the changing scale needed to be experienced visually rather than reported by separate interface elements.

After that point, I became much more willing to reject technically successful output. Later, I did the same when the paper height was mathematically doubling but visually appeared frozen, when the physical-limit wording was more certain than the evidence supported, and when the music feature worked but did not strengthen the main idea. The breakthrough was learning to treat “it works” as the beginning of evaluation, not the end.

## What did this work change about who I want to be as a software developer?

This assignment changed how I think about working with coding agents. Before, I focused mainly on how to give clear instructions so that the agent could produce the result I wanted. During this project, I realised that giving instructions is only one part of the work. The developer still needs to keep control of the overall direction of the project.

A coding agent can help with implementation very quickly, but it should not be responsible for deciding what the final product should become. I need to understand the main purpose of the project first, then use the agent to help realise that direction. This also means having enough judgement to evaluate the result rather than accepting it simply because it works. I need to be able to recognise when an interaction is confusing, when a design does not communicate the idea clearly enough, or when a feature is technically successful but does not actually make the product better.

This is the kind of developer I want to become. I want to use AI as a powerful implementation tool, while keeping responsibility for the larger decisions myself. For me, good software development is not only about producing working code. It is also about knowing what should be built, keeping the product moving in the right direction, and being able to judge whether the final result is genuinely good enough for the people who will use it.
